# Application logging

`src/core/logging.py` uses Python's standard logging library and adds no dependency.
Each event is one JSON line written to stdout for collection by the runtime.
Importing the module does not change logging or read configuration.

## Startup

The API and each worker process must configure logging before concurrent work:

```python
from src.core.config import get_settings
from src.core.logging import configure_logging

configure_logging()  # Capture configuration failures at the default INFO level.
settings = get_settings()
configure_logging(settings.log_level)
```

The second call applies `LOG_LEVEL` without adding duplicate root handlers.
Both calls replace and close existing root handlers; this function belongs in
process entry points, not imported libraries or request handlers. It preserves
named logger handlers. When adding a server such as Uvicorn, ensure its logging
configuration delegates to the root handler and does not independently install
handlers that duplicate or bypass this formatter. Review access logging before
enabling it: URLs and query strings can contain private information.

Application modules use ordinary loggers and deferred interpolation:

```python
import logging

logger = logging.getLogger(__name__)
logger.info("Document indexing completed")
```

Use DEBUG for safe diagnostic detail, INFO for lifecycle outcomes, WARNING for
recoverable problems, and ERROR for failed operations. Avoid per-chunk INFO logs.
Do not log private values at any level, including DEBUG.

## Tenant and user context

After the authentication layer verifies the JWT signature, issuer, audience,
expiry and identity claims, bind its trusted identifiers around request handling:

```python
from src.core.logging import log_context

# These variables come from verified claims; this example does not verify JWTs.
with log_context(tenant_id=tenant_id, user_id=user_id, request_id=request_id):
    logger.info("Document ingestion accepted")
```

Use internal opaque user identifiers, not email addresses. Request identifiers
should be generated by the application or validated by trusted ingress. Identifiers
must be nonempty strings of at most 256 characters with no whitespace or control
characters. A user identifier requires a tenant identifier. This is format
validation only: the context manager grants no permissions and does not verify JWTs.
Never bind identity directly from an unverified token, body, or tenant header.

The context exists only for the `with` scope and is restored on exceptions.
Nested scopes replace all identifiers, including omitted fields. Outside a scope,
identifiers are `null`, which is appropriate for startup and unauthenticated events.
Async tasks have independent context changes. Child tasks inherit their creator's
context: avoid detached request tasks, and explicitly bind a fresh scope for each
background job. Threads and processes need explicit propagation; each queue delivery
must bind tenant/user context after validating stored job ownership. No context
automatically travels through RabbitMQ.

Tenant context must be present when an event is emitted. Future queue-based log
handlers would need to capture it on the producing side, since this formatter
reads the current context synchronously. Do not use logging context as the source
of tenant identity for database queries or authorization.

## Output and sensitive data

Every event contains `timestamp` (UTC ISO 8601), `level`, `logger`, `message`,
`tenant_id`, `user_id`, and `request_id`. An exception adds its type and frame
locations (`file`, `function`, `line`). JSON escaping keeps embedded newlines
inside a single event rather than allowing forged output lines.

Only these fields are serialized. Arbitrary `extra` data, including attempts to
override identity, is ignored. Exception messages, locals, source code, exception
chains, and `stack_info` are deliberately omitted. For errors, use a safe message:

```python
try:
    process_document()
except RuntimeError:
    logger.exception("Document processing failed")
    raise
```

Defensive message redaction masks Bearer/Basic credentials, JWT-shaped tokens,
URL userinfo, and common password/token/API-key assignments. It applies after
message interpolation and does not modify the original LogRecord.
Pattern matching is a fallback, not a guarantee that arbitrary secrets or personal
data will be detected. Never log tokens, JWT claims dictionaries, request bodies,
document text, prompts, responses, configuration dumps, or `str(exception)`.
Use constant event messages and safe operational identifiers. Do not put secrets
in logger names or context identifiers. Other handlers and external integrations
need their own data controls; this module does not implement Langfuse redaction.

Process setup suppresses `pymongo.command` DEBUG/INFO events because command
bodies can include account hashes and private metadata. Do not re-enable them or
add raw token/password logging in local-auth handlers.

Tenant/user identifiers make logs sensitive operational data. Restrict access to
the log sink and configure retention there; tenant tagging does not isolate access
to a shared log sink.
